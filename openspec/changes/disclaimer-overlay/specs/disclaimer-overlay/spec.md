# Disclaimer Overlay Specification

## Purpose

Show an honest, non-intrusive disclaimer before the visitor can use the voice interview. It communicates that Mikel OS v2.0 is an experimental prototype — responses are generated by a RAG + LLM pipeline that can hallucinate, and the twin does not substitute a real interview with Mikel. Requiring explicit acknowledgment protects the project and reinforces trust by setting expectations.

## Requirements

### Requirement: Display disclaimer on load

When the frontend loads and the visitor has not previously acknowledged the disclaimer, the system SHALL display a full-screen overlay with the disclaimer text and a clear acceptance action.

#### Scenario: First visit

- GIVEN the visitor has not accepted the disclaimer before (no stored acknowledgment)
- WHEN the page loads
- THEN the disclaimer overlay is visible
- AND the interview controls (mic button) are not usable until acknowledged

#### Scenario: Returning visit (acknowledged)

- GIVEN the visitor already accepted the disclaimer in this browser
- WHEN the page loads
- THEN the disclaimer overlay is not shown
- AND the interview controls are immediately usable

### Requirement: Acknowledgment persistence

The system SHALL persist the acknowledgment in browser local storage so a returning visitor is not shown the overlay again.

#### Scenario: Accept action

- GIVEN the disclaimer overlay is visible
- WHEN the visitor clicks the accept button
- THEN the acknowledgment is written to local storage
- AND the overlay is hidden
- AND the interview controls become enabled

#### Scenario: Storage key namespacing

- GIVEN the application runtime
- THEN the local storage key for acknowledgment SHALL be namespaced (e.g., prefixed) to avoid collisions with other stored data
- AND clicking accept SHALL NOT clear or overwrite other unrelated local storage entries

### Requirement: Honest disclaimer copy

The disclaimer SHALL state, in clear Spanish matching the project tone, that the system is experimental, that answers come from an LLM which may hallucinate, and that it does not substitute a real interview with Mikel.

#### Scenario: Copy present

- GIVEN the overlay is rendered
- THEN it SHALL mention all three facts: experimental prototype, possible LLM hallucination, and not a substitute for a real interview

#### Scenario: Copy formatting

- GIVEN the overlay is rendered
- THEN the copy SHALL be readable, avoid alarmist language, and present the honesty as a quality signal rather than a liability
- AND the text SHALL be plain (no Markdown/emoji per the twin's tone rules), displayed in the UI's existing typography

### Requirement: Design consistency

The overlay SHALL reuse the existing frontend overlay pattern and design tokens so it looks native to "Mikel OS" rather than a third-party cookie banner.

#### Scenario: Reuses overlay styling

- GIVEN the overlay is shown
- THEN it SHALL use the existing `.overlay` container pattern and project CSS variables (colors, fonts) already defined in `style.css`

#### Scenario: Layering above audio prompt

- GIVEN audio may later be blocked by the browser
- WHEN the disclaimer is present
- THEN the disclaimer SHALL render above (higher z-index than) the existing audio-blocked overlay, ensuring the visitor resolves the disclaimer first

### Requirement: Non-intrusive on repeat views (SHOULD)

To keep the experience quality for a recruiter who returns, the permanence marker MAY be a small, persistent line under the status area once acknowledged, but the full overlay SHALL NOT reappear.

#### Scenario: Persistent reminder (optional)

- GIVEN the visitor has accepted the disclaimer
- WHEN the page loads
- THEN the full overlay is not shown
- AND a short fine-print note remains visible in the UI footer/status area reminding that it is an experimental prototype

## Out of Scope

- Backend API changes: the disclaimer is entirely client-side; no endpoint change is required.
- Formal legal text or GDPR consent (this is informational, not a personal-data consent flow).
- Server-side tracking of acknowledgment.

## Non-Goals / Rejected Alternatives

- **No-microcopy-only instead of modal:** a permanent microcopy line alone does not capture explicit acknowledgment; the modal is kept. The acknowledged persistent note MAY be added alongside.
- **No third-party banner styling:** the overlay is styled to match the existing UI, not to look like a generic cookie/tracking banner.
