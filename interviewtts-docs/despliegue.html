Capítulo 07

Despliegue en Producción

Restricciones reales: Oracle Free Tier ARM64, 4 cores, 24 GB RAM, $0/mes. Sin GPU, toda la inferencia CPU-bound. TLS obligatorio, Nginx y systemd tal como viven en el repositorio, y Docker como segunda vía.

La restricción: $0/mes

Uno de los objetivos del proyecto era demostrar que se puede construir un sistema de IA funcional sin gastar dinero en infraestructura. Esto es relevante para estudiantes sin presupuesto para GPUs, prototipos donde el costo no debe superar al MVP, y aprendizaje: cuando no puedes escalar con dinero, aprendes a escalar con ingeniería.

Oracle Free Tier ARM64

4Cores ARM64 (Ampere A1)
24 GBRAM compartida (hasta 4 instancias)
$0Costo mensual (siempre-disponible, no trial)

Oracle Cloud Free Tier ofrece cómputo ARM64 con hasta 4 OCPU y 24 GB de RAM siempre gratis. Es suficiente para correr todo el pipeline en carga de conversación única. Solo Whisper consume ~1,4 GB en memoria (valor aproximado del README), así que el margen es holgado para el modelo elegido — la restricción real es tiempo de CPU, no RAM.

ARM64 vs x86

ARM64 es una arquitectura RISC con mejor eficiencia energética. Para inferencia CPU ofrece buen balance precio/rendimiento. CTranslate2 y PyTorch tienen soporte nativo.

Ver también: cómo se eligió entre tamaños de Whisper bajo esta restricción, en el capítulo 02 — Whisper.

Sin GPU: CPU-bound

Sin GPU, toda la inferencia es CPU-bound. El impacto por componente: Whisper STT domina el presupuesto de cada turno (ver capítulo 02), los embeddings de RAG son rápidos (el embedder multilingüe actual son 384 dimensiones y cabe en CPU), y Edge TTS ni siquiera compite por la CPU local: sintetiza en el servicio de Microsoft y devuelve MP3 listo para servir, sin GPU propia.

El README lo resume: el presupuesto del pipeline ronda los 8 segundos en CPU, y es el endpoint de streaming el que hace que la experiencia se sienta responsiva pese a ello.

TLS no es opcional: sin certificado no hay micrófono

Antes de nada, una restricción que no es de configuración sino de la plataforma: la API de getUserMedia solo se sirve en contexto seguro. Sobre HTTP plano el navegador no concede acceso al micrófono, sin importar qué headers envíes. Y nginx/interview.conf no arranca sin certificado: el bloque 443 tiene ssl_certificate y nginx se niega a arrancar con "cannot load certificate". Es decir, el orden no es una preferencia, es la diferencia entre una app que funciona y una que no arranca.

Orden de despliegue TLS (ejecutable en el orden dado)
#PasoDetalle
1Certificado, con nginx aún sin escuchar en el 80certbot certonly --standalone --cert-name interviewtts -d <dominio>. --standalone occupies el puerto 80 él mismo, así que falla con "Address already in use" si algo ya escucha ahí: en un VPS nuevo nada escucha; si nginx está instalado y corriendo, páralo primero
2Instalar el conf y arrancar nginx por primera veznginx -t && systemctl enable --now nginx. enable --now, no reload: una instalación nueva tiene nginx deshabilitado y parado, y reload sobre una unidad parada no la arranca
3Solo entonces habilitar el return 301 del bloque 80Va comentado a propósito: activarlo con TLS roto cierra la puerta a todos los visitantes, incluido tú, y el sitio HTTP plano se vuelve inalcanzable

El --cert-name interviewtts no es cosmético. Sin él, certbot deriva el directorio de salida del primer -d, así que la forma simple escribe en /etc/letsencrypt/live/<dominio>/fullchain.pem —una ruta distinta de la que apunta el conf, y nginx se niega a arrancar. Nombrar el certificado desacopla el directorio del dominio, así que el conf es correcto para cualquier dominio y sigue siendo correcto cuando el dominio cambie. Y certbot renew re-emite a la misma ruta, así que nada de lo de abajo hay que cambiarlo cuando lo haga.

Revertir el paso 3 es fácil. Revertir la decisión HSTS que el navegador cacheó después de ver la cabecera, no.

Nginx: el conf real del repositorio

Este es el contenido de nginx/interview.conf, versión resumida pero fiel:

# nginx/interview.conf (espejo fiel) # Bloque 1: HTTP plano. Solo redirección. server { listen 80; server_name _; # Descomentar SOLO tras confirmar que el bloque 443 funciona: # return 301 https://$host$request_uri; } server { listen 443 ssl; server_name _; ssl_certificate /etc/letsencrypt/live/interviewtts/fullchain.pem; add_header X-Frame-Options "SAMEORIGIN" always; add_header X-Content-Type-Options "nosniff" always; add_header X-XSS-Protection "1; mode=block" always; } # Cabeceras de seguridad a nivel de server + gzip add_header X-Frame-Options "SAMEORIGIN" always; add_header X-Content-Type-Options "nosniff" always; add_header X-XSS-Protection "1; mode=block" always; add_header Strict-Transport-Security "max-age=31536000" always; gzip on; }

Cuatro detalles que importan:

  • proxy_buffering off: sin esto, Nginx acumula las respuestas en búfer y el streaming SSE se rompe (los eventos llegan a chorros tardíos).
  • client_max_body_size 6m: nginx pone 1 MB por defecto si la directiva falta, y la aplicación acepta 5. Esas dos capas no se negocian: la exterior corre primero y gana, así que una grabación de 1 a 5 MB la rechaza nginx con un 413 pelado antes de que FastAPI la vea. Y igualar tampoco basta, por el envelope multipart descrito en el propio conf. Un test parsea este fichero y lo compara con la constante de la aplicación, así que las dos capas no pueden divergir sin que se note.
  • proxy_read_timeout 300s: acota el hueco entre dos lecturas del upstream, no el tiempo total de respuesta. Con el modelo pequeño sobre CPU, una transcripción lenta pasa un rato largo en cero bytes. 300 s es cinco veces el techo de 60 s de MAX_AUDIO_DURATION, y un test falla si los dos se encuentran. Esto es el techo, no el arreglo: el keepalive de 15 s es lo que sostiene la conexión, y 300 s holga para veinte intervalos.
  • /audio/ repite las cabeceras a propósito: nginx no hereda las add_header del padre en un bloque que declara las suyas, así que sin repetirlas el bloque 443 las perdería ahí —HSTS en particular debe llegar a toda respuesta para valer algo—.

Systemd: la unidad real, con hardening

# deployment/interviewtts.service (espejo fiel) [Service] Type=simple User=interviewtts WorkingDirectory=/opt/interviewtts # --host 127.0.0.1: el backend solo es alcanzable desde el proxy # local. Con 0.0.0.0 la API quedaba expuesta, saltándose nginx # y con él cada control de TLS, headers y rate-limit configurado ahí. # --forwarded-allow-ips DEBE seguir limitado a 127.0.0.1: es la lista # de pares cuya X-Forwarded-For se cree. Ampliarlo (p. ej. a "*") # dejaría que CUALQUIER cliente falsifique su propia dirección. ExecStart=/opt/interviewtts/venv/bin/uvicorn backend.main:app --host 127.0.0.1 --port 8000 --proxy-headers --forwarded-allow-ips 127.0.0.1 Restart=always RestartSec=5 # El primer arranque descarga ~1 GB de modelos. El default de 90 s # mata esa descarga en un enlace lento y, con Restart=always # arriba, reinicia en bucle cada 5 s hasta llenar la caché. TimeoutStartSec=10min Environment=PYTHONUNBUFFERED=1 Environment=HOME=/opt/interviewtts EnvironmentFile=/opt/interviewtts/.env # Hardening NoNewPrivileges=true ProtectSystem=strict ProtectHome=true ReadWritePaths=/opt/interviewtts/audio /opt/interviewtts/data /opt/interviewtts/reports /opt/interviewtts/backend/.rag_cache -/opt/interviewtts/.cache/huggingface PrivateTmp=true

Dos decisiones que no son óbvias:

  • HOME se declara, no se hereda. La caché del modelo de embeddings vive bajo él. El usuario se crea con --home-dir /opt/interviewtts y systemd lo poblaría solo desde esa entrada de passwd —pero "lo haría" es exactamente el problema: la entrada de ReadWritePaths de arriba es una ruta absoluta que dice dónde tiene que acabar esa resolución, y si algún día se moviera, las dos discreparían en silencio y el modelo se volvería a descargar a un directorio de solo lectura en cada arranque. Declarado aquí, un test los contrasta.
  • ProtectHome=true no pelea con esto: vuelve de solo lectura /home, /root y /run/user, y el home de este usuario es /opt/interviewtts, fuera de las tres. Es ProtectSystem=strict quien vuelve de solo lectura también /opt/interviewtts, y eso es lo que estas rutas vuelven a abrir.

El gotcha de ProtectSystem=strict: deja TODO el sistema de archivos en solo lectura salvo lo listado en ReadWritePaths. Son cinco entradas, no tres, y las dos últimas llevan el prefijo - de "ignorar si falta" por razones distintas. El capítulo 06 — Persistencia y memoria explica cada una.

Docker: la segunda vía de despliegue

El despliegue no es solo systemd. El repositorio trae Dockerfile y docker-compose.yml para despliegue local, y el Dockerfile se escribió como espejo de la unidad: mismo punto de entrada, misma postura sin root, mismo conjunto de rutas de escritura —expresado como contenedor en lugar de unidad systemd.

  • Una sola arquitectura. No hay buildx, ni --platform, ni manifest list: la imagen es de arquitectura única. No es un descuido pendiente de resolver; es que nunca hizo falta en este despliegue, que corre en Docker Desktop sobre Windows. La consecuencia práctica es que la imagen no es multi-arch y no debe asumirse que lo sea.
  • Base python:3.10-slim, no 3.11. slim para reducir tamaño; ffmpeg y ca-certificates como dependencias de runtime, no de build: faster-whisper le pasa la grabación a ffmpeg para decodificar, y sin CA el TLS de edge-tts y de httpx hacia OpenRouter no funciona.
  • Torch desde el índice de CPU, instalado y fijado en su propia capa antes del proyecto, vía --extra-index-url y no --index-url. Con PyPI solo, la resolución trae la build CUDA y arrastra el stack nvidia-*: varios GB de descarga, todos peso muerto para un servicio configurado con WHISPER_DEVICE=cpu. Como índice extra, PyPI sigue sirviendo el resto y la ordenación de versiones local de PEP 420 hace que gane la rueda CPU sin necesidad de fijar nada.
  • El COPY es explícito, no COPY . .: .dockerignore ya excluye secretos y PII, y un COPY amplio haría que ese fichero fuera lo único entre la OPENROUTER_API_KEY y una capa publicada. Dos rutas fijas que faltan fallan ruidosamente; COPY . . falla en silencio cuando alguien olvida una.
  • Los volúmenes con nombre nacen de la imagen. Un volumen con nombre montado sobre una ruta que no existe se crea como root y un servicio sin root no puede escribir — así es como la caché de HuggingFace se convierte en una redescarga de 457 MB en cada up. Los directorios se crean y se cambian de dueño en la imagen, y Docker siembra el volumen desde ella preservando el propietario.
  • --host 0.0.0.0 dentro del contenedor, sustituyendo el 127.0.0.1 de la unidad: el loopback de un contenedor es su propio espacio de nombres, así que atarlo lo haría inalcanzable desde fuera del contenedor diga lo que diga el publish. El aislamiento que daba el loopback lo hace la publicación en su lado de host.

El HEALTHCHECK tiene un start-period de 900 s y es portante: el primer arranque no es lento porque la app lo sea, sino porque HuggingFace tiene que descargar los modelos entonces. Docker mata un contenedor que falla su healthcheck, así que un periodo calibrado sobre una caché caliente convierte el primer arranque en frío en un bucle de reinicios. Y lo que afirma es alcanzabilidad, no corrección: /api/health devuelve 200 incluso con status: "degraded" en el cuerpo, y eso es correcto, porque reporta rag_mode y problems precisamente para que un pipeline que cayó a TF-IDF sea visible mientras el proceso sigue sirviendo.

El script de despliegue y su vuelta atrás

scripts/deploy.sh (168 líneas) encadena el ciclo completo —validar → compilar → rsync → reiniciar— y aborta al primer fallo con set -euo pipefail. La secuencia tiene una pieza poco evidente: el mv servidor previo al rsync crea el directorio, no lo transfiere, y preserva el árbol vivo actual como la única copia de rollback en candidate.prev/.

Ese orden protege contra un fallo concreto: si el destino se creara dentro del rsync, el --delete borraría la única copia de rollback antes de que el propio rsync que la va a sustituir haya corrido. Y hay un subcomando rollback explícito, que restaura candidate.prev/ sobre el árbol vivo.

La ambigüedad de wiki/ en el arranque

El cargador de perfil decide su fuente con una sola comprobación: si el directorio wiki/ existe, lo lee; si no, cae a los Markdown de candidate/. No hay bandera, ni aviso, ni forma de que el llamador diga cuál quería. En el despliegue eso significa que el contenido real de la entrevista depende de si ese directorio llegó por el rsync, y un fallo silencioso del despliegue se manifestaría como un gemelo que responde con otro corpus —no como un error.

Aviso sobre las instrucciones del README

Los dos comandos de clonado del README clonan el repositorio original, no la rama de trabajo con estas mejoras: apuntan a la URL del proyecto upstream. Quien siga esos pasos al pie de la letra despliega el código anterior. La diferencia no es un matiz de documentación: el despliegue tiene que fijar la rama de forma explícita para poder publicar este proyecto.

Copia de seguridad

Todo el estado durable cabe en dos rutas: data/interviewtts.db (la base WAL) y reports/ (transcripciones Markdown). Copiar ambas con el servicio detenido — o usando BACKUP de SQLite — captura conversaciones, turnos e informes completos. El audio y la caché de embeddings son regenerables y no merecen espacio de backup.
