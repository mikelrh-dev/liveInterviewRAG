Capítulo 08

Aprendizajes y Reflexión

Lo aprendido construyendo esto: FastAPI async, Docker en ARM64, RAG desde cero, TDD con 256 tests — y las lecciones que solo aparecen cuando algo se rompe.

Patrones async de FastAPI

FastAPI no es solo un framework HTTP. Su soporte nativo para async/await y StreamingResponse lo convierte en un orquestador ideal para pipelines de IA.

Lo aprendido:

  • async no es magia: si tu componente bloquea (como Whisper en CPU), necesitas asyncio.to_thread o un executor para no bloquear el event loop.
  • StreamingResponse es perfecto para SSE: emite eventos a medida que se generan, sin acumular la respuesta entera.
  • El puente thread→loop importa: correr el LLM en un executor exige devolver los tokens al event loop con una cola thread-safe (call_soon_threadsafe) — un detalle que ningún tutorial menciona hasta que lo necesitas.

Docker por prueba y error

Docker fue una de las partes más frustrantes y formativas del proyecto. El problema: ARM64. Muchas imágenes Docker no están compiladas para ARM64, y las que están pueden tener problemas sutiles.

Aprendí a:

  • Construir imágenes multi-arch con docker buildx
  • Usar python:3.11-slim en lugar de imágenes full para reducir tamaño
  • Montar volúmenes para los embeddings persistidos
  • Manejar dependencias del sistema (librerías nativas y codecs) que varían entre arquitecturas

Arquitectura RAG desde cero

Antes de este proyecto, RAG era solo un concepto leído por ahí. Ahora se entiende como un sistema de ingeniería con componentes concretos:

  • Chunking: No es trivial. La estrategia de división afecta directamente la calidad de recuperación.
  • Embeddings: Elegir el modelo correcto importa. all-MiniLM-L6-v2 es el punto dulce para CPU.
  • Metadatos: El frontmatter YAML permite filtrado por tipo antes de gastar similitudes.
  • Persistencia: Calcular embeddings es costoso; persistirlos en disco es obligatorio.
  • Invalidación: SHA256 de los documentos: simple y efectivo.

Ver también: cada uno de estos componentes en detalle, en el capítulo 03 — RAG.

TDD: 256 tests

El proyecto tiene 256 tests pasando, escritos siguiendo el ciclo estricto: rojo → verde → refactor.

  • Rojo: Escribo el test primero. Falla porque la funcionalidad no existe.
  • Verde: Implemento lo mínimo necesario para que pase.
  • Refactor: Limpio el código sin cambiar el comportamiento.

La conclusión: TDD no va sobre tests. Va sobre diseñar antes de implementar. Cada test es un mini-diseño de cómo debería funcionar el código.

Disciplina TDD

La tentación de "escribir el código primero y los tests después" es constante. Pero cada vez que cede, el código resultante era peor: más acoplado, menos claro, más difícil de cambiar. TDD fuerza una separación natural de responsabilidades.

Especificación de papel ≠ silicio real

Versión temprana de este dossier presumía de float16 «porque hay RAM de sobra». La realidad: CTranslate2 rechaza float16 en CPUs sin soporte FP16 eficiente con un ValueError. La memoria nunca fue la restricción — el hardware disponible sí.

  • int8 ganó por portabilidad: funciona en cualquier CPU moderna; float16 solo donde hay aceleración FP16.
  • Las specs venden promedios: "float16 es más rápido" es cierto en algunos chips y falso en otros. La única spec confiable es la tuya medida en tu máquina.
  • Cambiar de opinión es señal de salud: small + int8 salió a producción porque sobrevivió al contacto con el hardware real, no al papel.

Ver también: la historia completa en el capítulo 02 — Whisper.

Nunca hables con la voz de tus datos crudos

Un bug temprano y formativo: concatenar la salida cruda de recuperación de RAG a la respuesta hizo que el TTS leyera literalmente "[Source: cv.md | Tipo: experience]" al reclutador.

  • Dos canales, dos formatos: lo que ve el panel de contexto (metadatos, fuentes, scores) y lo que se pronuncia (texto limpio y saneado) son contratos distintos. Mezclarlos produce momentos surrealistas.
  • Saneamiento como barrera obligatoria: hoy todo texto pasa por sanitize_for_tts (fuera Markdown y emojis) antes de sintetizarse.
  • Los bugs embarazosos enseñan más: nadie olvida el día en que su gemelo lee metadatos en voz alta.

Ver también: el contrato actual de chunks-solo-al-panel, en el capítulo 05 — Caché.

Revisa tu documentación como código

Una auditoría técnica adversarial sobre este dossier encontró fabricaciones factuales: float16 presentado como decisión enviada, un "entity boost" que nunca existió en el código, un parámetro top_p que jamás se envió, Pocket TTS acreditado como motor activo y un conteo de tests desactualizado (155+, cuando son 256).

  • La documentación también es código: se le escapan bugs igual — solo que sus bugs se llaman mentiras involuntarias.
  • La revisión adversarial funciona: contrastar cada afirmación contra la fuente (grep incluido) atrapa lo que la auto-revisión normaliza.
  • Números sin método = rumores: toda cifra de este dossier ahora declara cómo se obtuvo o se marca explícitamente como estimado.

Decisiones de producto bajo restricciones

Las mejores lecciones vinieron de las restricciones:

  • $0/mes: me obligó a buscar alternativas open source y a optimizar lo que ya tenía.
  • Sin GPU: me enseñó a medir y optimizar cada fase del pipeline.
  • ARM64: me expuso a problemas reales de compatibilidad entre arquitecturas.
  • Solo CPU: me mostró que la ingeniería correcta puede compensar hardware limitado.

Las restricciones no son enemigas. Son maestras: fuerzan a ser creativo, a entender realmente los sistemas con los que trabajas, y a tomar decisiones informadas en lugar de al azar.

Glosario mínimo

Embedding
Representación de un texto como vector numérico (aquí, 384 dimensiones) que captura su significado. Textos parecidos producen vectores cercanos.
Cuantización
Reducir la precisión numérica de los pesos de un modelo (float32 → int8) para ahorrar memoria y cómputo, perdiendo poca precisión.
WAL
Write-Ahead Logging: modo de SQLite donde las escrituras van primero a un registro. Efecto práctico: lectores y escritor no se bloquean entre sí.
RAG
Retrieval-Augmented Generation: recuperar documentos relevantes y entregárselos al LLM como contexto para que responda con datos reales en vez de memoria entrenada.
SSE
Server-Sent Events: protocolo HTTP unidireccional servidor→cliente, ideal para streaming de tokens y fragmentos de audio.
Similitud coseno
Métrica de parecido entre dos vectores según su ángulo, ignorando magnitud: 1 significa misma dirección, 0 nada en común.
