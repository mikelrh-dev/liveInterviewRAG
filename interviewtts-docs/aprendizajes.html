Capitulo 07

Aprendizajes y Reflexion

Lo que aprendi construyendo esto: FastAPI async, Docker, RAG desde cero, TDD con 155+ tests, y decisiones de producto bajo restricciones.

FastAPI Async Patterns

FastAPI no es solo un framework HTTP. Su soporte nativo para async/await y StreamingResponse lo convierte en un orquestador ideal para pipelines de IA.

Lo que aprendi:

  • async no es magia: Si tu componente bloquea (como Whisper en CPU), necesitas run_in_executor para no bloquear el event loop
  • StreamingResponse es perfecto para SSE: yields tokens a medida que se generan
  • Background tasks sirven para invalidar caches sin bloquear la respuesta al cliente

Docker por Prueba y Error

Docker fue una de las partes mas frustrantes y formativas del proyecto. El problema: ARM64. Muchas imagenes Docker no estan compiladas para ARM64, y las que estan pueden tener problemas sutiles.

Aprendi a:

  • Construir imagenes multi-arch con docker buildx
  • Usar python:3.11-slim en lugar de imagenes full para reducir tamano
  • Montar volumes para embeddings persistidos
  • Manejar dependencias del sistema (libros, codecs) que varian entre arquitecturas

Arquitectura RAG Desde Cero

Antes de este proyecto, RAG era solo un concepto que habia leido. Ahora lo entiendo como un sistema de ingenieria con componentes concretos:

  • Chunking: No es trivial. La estrategia de division afecta directamente la calidad de recuperacion
  • Embeddings: Elegir el modelo correcto importa. all-MiniLM-L6-v2 es el sweet spot para CPU
  • Metadata: El frontmatter YAML es poderoso para filtrado y boost
  • Persistencia: Calcular embeddings es costoso; persistirlos en disco es obligatorio
  • Invalidacion: SHA256 de documentos es simple y efectivo

TDD: 155+ Tests

El proyecto tiene 155+ tests siguiendo el ciclo estricto: rojo - verde - refactor.

  • Rojo: Escribo el test primero. Falla porque la funcionalidad no existe.
  • Verde: Implemento lo minimo necesario para que pase.
  • Refactor: Limpio el codigo sin cambiar el comportamiento.

Lo que aprendi: TDD no es sobre tests. Es sobre diseñar antes de implementar. Cada test es un mini-diseno de como deberia funcionar el codigo.

Disciplina TDD

La tentacion de "escribir el codigo primero y los tests despues" es constante. Pero cada vez que cedi, el codigo resultante era peor: mas acoplado, menos claro, mas dificil de cambiar. TDD fuerza una separation of concerns natural.

Orquestacion Multi-Proveedor

Diseñar un sistema que funcione con multiples proveedores de LLM (Google AI, OpenRouter) me enseno sobre abstraccion y degradacion elegante.

El patron es simple pero poderoso: un adaptador por proveedor, una interfaz comun, y un fallback automatico. Si el primario falla, el secundario toma el control sin que el usuario note nada.

SSE vs WebSockets

Elegir SSE sobre WebSockets fue una decision basada en analisis del caso de uso, no en preferencia personal.

WebSockets son perfectos para chat bidireccional. Pero nuestro flujo es: cliente envia audio (POST), servidor responde con streaming de audio (SSE). Es fundamentalmente unidireccional durante la fase de respuesta. SSE es la herramienta correcta.

OpenSpec: Spec-Driven Development

Usar OpenSpec para documentar decisiones arquitectonicas antes de implementar cambio la forma en que trabajo. Escribir que voy a hacer antes de hacerlo me obliga a pensar en edge cases, tradeoffs, y consecuencias.

Las specs no son burocracia. Son contratos con mi futuro yo.

Decisiones de Producto Bajo Restricciones

Las mejores lecciones vinieron de las restricciones:

  • $0/mes: Me obligo a buscar alternativas open source y a optimizar lo que ya tenia
  • Sin GPU: Me enseño a medir y optimizar cada milisegundo del pipeline
  • ARM64: Me expuso a problemas reales de compatibilidad entre arquitecturas
  • Solo CPU: Me mostro que la ingenieria correcta puede compensar hardware limitado

Las restricciones no son enemigas. Son maestras. Te fuerzan a ser creativo, a entender realmente los sistemas con los que trabajas, y a tomar decisiones informadas en lugar de random.
